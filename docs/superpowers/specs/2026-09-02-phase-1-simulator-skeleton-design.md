# Фаза 1 — скелет симулятора

Дата: 2026-09-02. Источник требований: [../../brief.md](../../brief.md), §4 и §12.

## Цель

Одна страница: three.js, загруженный URDF робота, шесть ползунков на суставы,
орбитальная камера, сетка и стол. Больше ничего.

**Definition of Done (из брифа):** модель грузится меньше чем за 2 секунды,
суставы двигаются, пределы суставов соблюдаются, 60 fps на среднем ноутбуке.

## Решение по отсутствующим данным

URDF, меши и брендбук PROMPOWER пока не получены. Собрано два плагина, оба
временные, оба показывают пользователю предупреждение о том, чем они не являются.

`placeholder-6dof` — URDF из примитивов, написанный с нуля, без геометрии JAKA и
без выдуманных характеристик PROMPOWER. Мешей нет вовсе. Полезен как пример
минимального плагина и как быстрый объект для тестов.

`jaka-6dof` — активная модель. Шестиосевой кобот JAKA из
[Haoyi-SJTU/jaka_description](https://github.com/Haoyi-SJTU/jaka_description) под
MIT. Взят по прямому разрешению заказчика, снявшего запрет из §11 брифа.
Официальные репозитории JAKA лицензии не имеют вовсе; MIT здесь проставлен
сторонним автором, а не правообладателем геометрии, поэтому для продакшена нужны
файлы от PROMPOWER. Материалы в URDF переименованы в `pp_base` / `pp_joint` /
`pp_accent`, чтобы робот красился из палитры плагина, а не в цвета JAKA.

Подстановка настоящего робота — новый каталог плагина и одна строка в
`sandbox-client.tsx`, код вьюера не трогаем.

## Архитектура

Монорепозиторий на npm workspaces. Корень репозитория — одновременно приложение
Next.js и корень воркспейсов; пакеты в `packages/*` подключаются как
`@prompower/*` и транспилируются Next через `transpilePackages`, отдельного шага
сборки у пакетов нет.

```
prompower-academy/
├── app/[locale]/sandbox/     страница фазы 1
├── components/simulator/     React + three.js: сцена, робот, панель ползунков
├── packages/
│   ├── sim-core/             чистая логика, без React и без three.js
│   └── robot-plugins/
│       └── placeholder-6dof/ конфиг плагина + URDF
├── public/models/placeholder-6dof/
├── scripts/convert-meshes.ts
└── messages/{ru,en}.json     next-intl
```

`components/` и `scripts/` в дереве брифа не перечислены, но брифу не противоречат:
§4.1 прямо требует `scripts/convert-meshes.ts`, а компоненты вьюера завязаны на
three.js и потому не могут лежать в `sim-core`.

### Границы модулей

| Модуль | Что делает | От чего зависит |
|---|---|---|
| `@prompower/sim-core` | Типы суставов, зажим значений в пределы, нормализация углов | ничего |
| `@prompower/robot-plugins/*` | Описание модели: id, имя, путь к URDF, порядок суставов, домашняя поза, палитра, параметры сцены | `sim-core` (только типы) |
| `components/simulator` | Загрузка URDF, сцена, камера, стол, ползунки | three.js, R3F, urdf-loader, оба пакета выше |

Поток данных однонаправленный: панель ползунков → `clampJointVector` из
`sim-core` → состояние React → императивная запись углов в `URDFRobot` через ref.
Сцена не хранит собственную копию углов, единственный источник истины — состояние
страницы.

### Контракт плагина модели

```ts
interface RobotPlugin {
  id: string;                    // slug каталога
  displayNameKey: string;        // ключ next-intl, не готовая строка
  isPlaceholder: boolean;
  urdfUrl: string;
  packages: Record<string, string>;  // для loader.packages
  joints: JointDescriptor[];     // порядок = порядок ползунков
  homePose: number[];            // радианы, длина = joints.length
  palette: { base: string; joint: string; accent: string };
  scene: { tableHeight: number; tableSize: [number, number]; cameraDistance: number };
}
```

Ни одна характеристика робота в коде не появляется: пределы суставов читаются из
URDF при загрузке, всё остальное — из этого конфига.

## Обработка ошибок

Ошибки — на границе загрузки. Если URDF не найден, не разбирается или в нём нет
объявленных в плагине суставов, страница показывает человеческое сообщение и
список того, что не сошлось, вместо пустого чёрного канваса. Расхождение между
`joints` плагина и суставами URDF — ошибка загрузки, а не тихое игнорирование.

## Тестирование

- **Vitest, `sim-core`:** зажим в пределы (внутри диапазона, ниже, выше, на
  границе, NaN), непрерывный сустав без пределов, несовпадение длины вектора.
- **Vitest, адаптер:** извлечение пределов из объекта, структурно совместимого с
  `URDFRobot`, — без импорта three.js в тест.
- **Playwright:** страница `/ru/sandbox` открывается, канвас есть, ползунок
  двигается, значение упирается в предел и не идёт дальше.

## Конвейер мешей

Меши моделей не лежат в репозитории готовыми: `scripts/convert-meshes.ts` берёт
исходные STL или glTF из плагина, жмёт их в glTF с Draco, переписывает ссылки в
URDF на относительные и раскладывает результат в `public/models/<плагин>/`.
Проверяется бюджет 3 МБ на модель, превышение возвращает ненулевой код. На модели
JAKA конвейер даёт 2.62 МБ → 0.22 МБ.

`urdf-loader` из коробки понимает только STL и DAE, поэтому glTF грузится своим
`loadMeshCb` через `GLTFLoader` с `DRACOLoader`; декодер кладётся в `public/draco`
на postinstall, а не тянется с чужого CDN — хостинг только российский.

Отдельный момент, который легко пропустить: `urdf-loader` сообщает о готовности
сразу после разбора XML, когда меши ещё летят по сети. Мерить в этот момент
нечего — габариты выходят пустыми, а время загрузки заниженным. Поэтому хук
считает незакрытые запросы мешей и объявляет модель готовой только когда их не
осталось.

## Что в фазу 1 не входит

Blockly, интерпретатор, IK, коллизии, аутентификация, БД, уроки, лендинг. Всё это
фазы 2 и дальше.

## Что придётся пересмотреть в фазе 2

Сейчас пределы суставов извлекаются из объекта, который построил `urdf-loader`,
то есть кинематическое описание робота живёт только внутри three.js. Для фазы 1
этого достаточно: `sim-core` остаётся чистым, адаптер проверяется обычными
объектами.

В фазе 2 этого станет мало. Интерпретатору нужна прямая кинематика, а ей —
смещения звеньев и оси суставов из URDF. Если они по-прежнему будут доступны
только через three.js, то обещание гонять задания уроков в CI без браузера
сломается. Поэтому первой задачей фазы 2 идёт собственный разбор URDF внутри
`sim-core`: текст URDF читается один раз и отдаётся двум потребителям — парсеру
`sim-core` (кинематика, пределы) и `URDFLoader.parse` (визуал). Тогда адаптер
`extractJointLimits` уходит, а пределы приходят из ядра.

Раньше времени это не делается: сегодня у такого парсера нет ни одного
потребителя, кроме пределов, которые `urdf-loader` и так уже разобрал.

## Открытые вопросы к заказчику

1. Модели линейки PROMPOWER и slug первой из них.
2. Формат поставки URDF и мешей, вид путей внутри URDF.
3. Брендбук: HEX акцента и нейтральной шкалы, шрифты, логотип.
4. Гриппер базовой поставки (нужно к фазе 2).
5. Существующие обучающие материалы (нужно к фазе 3).
